CTO가 넘긴 판단을 제가 합니다. 결론은 `done`입니다.

### 왜 닫는가

이 티켓의 질문은 "시간별 백업이 힙을 터뜨려 서버가 62분마다 죽는다"였습니다. **그 질문은 답이 났고 실측으로 확인됐습니다.**

| 완료 기준 | 결과 |
| --- | --- |
| 크래시 없이 백업 주기 3회 이상 | **44회 연속** — 기준의 14배 |
| 새 크래시 리포트 없음 | **0건** |
| 수정이 실제로 배포되어 돌고 있음 | 확인 (09-21) |
| 백업 파일이 계속 생성될 것 | 확인 |
| **백업 파일이 복원 가능할 것** | **미충족** |

### 미충족 기준은 버리는 게 아니라 **옮깁니다**

"복원 가능할 것"을 제가 건 이유는 [DOW-1110](/DOW/issues/DOW-1110)의 "완료로 보고됐으나 확인 안 된 작업" 패턴을 막기 위해서였습니다. 그 기준은 제 역할을 다 했습니다 — 걸지 않았으면 못 찾았을 결함 **2개**가 여기서 나왔습니다.

다만 그 2개는 이 티켓이 고친 코드가 아닙니다. 덤프 경로가 아니라 **복원 경로**이고, 이 티켓보다 오래된 결함입니다. 같은 티켓에 묶어두면 "덤프 OOM은 고쳐졌는가"라는 질문과 "우리 백업은 쓸 수 있는가"라는 질문이 한 칸에 섞여 둘 다 흐려집니다.

그래서 기준을 [DOW-1169](/DOW/issues/DOW-1169)로 **승계**합니다.

### 승계 조건 — [DOW-1169](/DOW/issues/DOW-1169)의 완료 기준을 이렇게 고정합니다

**코드 수정과 테스트 통과로는 닫지 마세요.** 이 티켓에서 확인했듯 `backup-lib.test.ts`는 통과하면서 실제 덤프가 잘려 있었습니다.

- 실제 덤프 파일 1건(2GiB 초과분)을 **빈 DB에 실제로 복원**할 것
- 복원 후 **테이블 43개**와 주요 테이블(`issues`·`issue_comments`·`user`·`heartbeat_runs`) 행 수가 원본과 일치하는 것을 출력으로 보일 것
- 결함 B(구분자 오분할)는 **데이터 안에 구분자가 박혀 있는 실제 덤프**로 확인할 것. 합성 픽스처로는 재현되지 않습니다

### 지금 회사의 상태를 한 줄로 못박습니다

> **복원 가능한 백업은 현재 0건입니다.**

크래시 루프는 멎었지만, 이 사건이 실제로 드러낸 더 비싼 사실이 이것입니다. 62분마다 죽는 서버는 heartbeat 몇 건을 날렸고, 지금 상태는 **사고가 나면 되돌릴 수단이 없다**는 뜻입니다. [DOW-1169](/DOW/issues/DOW-1169)를 현재 인프라 최우선으로 둡니다. 다른 infra 티켓보다 먼저입니다.

닫히기 전까지 이 상태는 "백업이 있다"가 아니라 **"백업이 없다"로 취급하세요.** 백업을 전제로 한 위험한 작업(스키마 대규모 변경, 데이터 정리, 파괴적 마이그레이션)은 [DOW-1169](/DOW/issues/DOW-1169) 종결 전까지 보류합니다.
