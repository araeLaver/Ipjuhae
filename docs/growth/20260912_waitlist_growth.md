- 소유자: 사업개발. 2026-09-20 CMO에서 인계
- 상태: 내부 성장 제안서. 게시·개발 일정 미승인
- 검토일: 2026-09-12, 2026-09-20 소유자 이관 확인 — 본문 내용 변경 없음
- 남은 검토 항목: 원조회 결과·시각·시간대·기간 복원, 내부 트래픽 구분, 채널 게시 이력, 제품 현행 동작, CTO 공수 검토, 보드 게시 결정

## 1. 원초안에 기록된 조회값과 한계

원작성자는 2026-09-12에 프로덕션 DB(`ipjuhae-production`, 스키마 `ipjuhae`)를 직접 조회했다고 기록했다. 이번 검수에서는 DB를 재조회하지 않았다. 정확한 조회 시각·시간대와 원결과 파일은 제공되지 않아 아래 수치는 재검증 전 기록값이다. 날짜 조건 없는 아래 SQL의 범위는 조회 시점까지 저장된 전체 행이며, 수집 시작일은 미상이다.

| 항목 | 원초안 기록값 | 집계 단위·기간·한계 |
| --- | --- | --- |
| 사전 신청 누적 | 1 (등록일 2026-09-04, UTM 없음) | `waitlist` 행 수. 고유 인원 중복제거 여부 미확인 |
| `page_view` | 225 | `analytics_events` 이벤트 행 수. 고유 방문자·세션 수 아님 |
| 경로 기록이 있는 `page_view` | 14 (`/` 12, `/preview` 2) | 경로가 존재하는 이벤트 행. 경로 누락 211행의 원인은 미검증 |
| UTM이 붙은 방문 | 0 | 원초안 표현. UTM 유무의 빈 문자열 처리 및 원조회 조건 재확인 필요 |
| referrer가 있는 방문 | 0 | 조회 SQL 미첨부. 누락값만으로 실제 direct 유입을 확정할 수 없음 |
| 기능 요구사항 접수 | 0 | 대상 테이블·기간·조회 SQL 미첨부 |
| 최근 방문 기록 | 09-09 3회, 09-10~12 0회 | 일별 이벤트로 추정되나 시간대·SQL 미첨부. 09-12는 조회 시각까지의 부분 일자 |

원초안은 경로 누락을 커밋 `7dbc64f6`(09-05) 이전 계측 탓으로 설명했으나 이벤트 시각별 검증이 필요하다. 경로 존재만으로 계측 이후 전체 방문을 대표한다고 볼 수 없다. 내부 방문이 대부분이라는 주장은 식별 근거가 없어 **가설**로 남긴다.

보관된 원초안 SQL(조회 결과를 이번 검수에서 재현하지 않음):

```sql
SET search_path TO ipjuhae, public;
SELECT COALESCE(properties->>'utm_source','(none)') AS src, COUNT(*)
FROM analytics_events WHERE event_name = 'page_view' GROUP BY 1 ORDER BY 2 DESC;
SELECT COALESCE(utm_source,'(none)') AS src, COUNT(*) FROM waitlist GROUP BY 1;
```

후속 조회는 시작·종료 시각과 시간대, 이벤트/세션/고유 인원 단위, 내부 트래픽 제외 규칙, 빈 UTM 처리, 동의·추적 누락을 기록한다. 원초안의 접속 경로는 `flyctl ssh console -a ipjuhae-production`이며 접속·조회는 이번 문서 검수에 포함하지 않았다.

## 2. 우선순위 제안과 검증 가설

기록된 이벤트가 적어 유입 확대 실험을 우선 제안한다. 다만 트래픽만이 병목이라는 결론이나 랜딩 개선이 무효라는 결론은 내릴 수 없다. 신청 1행과 서로 다른 기간의 경로 이벤트 14행을 나눠 전환율로 사용하지 않는다.

| 제안 | 가설·검증 방법 | 선행조건 |
| --- | --- | --- |
| A1. 프로필 UTM과 릴스 첫 게시 | 짧은 영상이 신규 도달에 기여하는지 캐러셀·텍스트와 비교 | 실제 채널 게시 이력·팔로워 수, 소재 사실확인, 보드 게시 결정 |
| A2. 관련 질문에 유용한 답글 | 일 10개는 실험 상한 제안. 프로필 유입 변화 관찰 | 채널 운영 규칙·담당자·응답 품질 검토 |
| A3. 신청 완료·결과 화면 공유 기능 | 카카오톡 공유가 추가 유입을 만드는지 `utm_source=kakao_share`로 관찰 | 현행 공유 동작 확인, CTO 설계·보안·공수 검토 |
| B1. 히어로 이메일 입력 | 폼 이동 감소가 완료율에 기여하는지 확인 | 동의 전 수집·저장 방지 및 제출 흐름 검토 |
| B2. 선택 이름·휴대폰 접기 | 선택 항목 축소가 완료율에 미치는 영향 확인 | 접근성·필수 동의·오류 처리 유지 검토 |
| B3. 신청 후 점검표 제공 | 자료의 유용성과 공유 행동 관찰 | 원고 검증, 안전보장으로 오인되지 않는 표현 |
| B4. 미리보기 링크 위치 변경 | 미리보기 사용과 신청 완료를 함께 측정 | 기존 탐색 기능의 가치와 이탈 원인 검증 |
| C1. `/risk` 공개범위 검토 | 실데이터 연결 또는 예시 데이터 시연 범위 비교 | 현행 fixture·데모 표시·`noindex`를 CTO가 확인. 실데이터 정확성·이용조건 검토 |
| C2. `/guide/[slug]` 콘텐츠 제안 | 검색 색인·노출·유입을 순서대로 측정 | 기존 sitemap 확인, 원고 사실확인, 웹 편집·개발 공수 검토 |

참조할 코드: `components/landing/waitlist-landing.tsx`, `app/risk/page.tsx`, `components/risk/risk-check.tsx`, `app/api/rental-risk/brief/route.ts`, `fixtures/rental-risk-sample.ts`. 원초안의 코드 진단은 이번에 재검증하지 않았으며 구현 약속이 아니다. 반나절·오늘 가능·2~3주 등 미산정 공수는 확정 일정에서 제외한다.

원초안의 원고 43건·만화 12화·릴스 8화는 자산 목록 재집계가 필요하다. **게시 0건은 채널 로그 미확보로 미확인**이다. 짧은 영상만 비팔로워에 도달한다는 주장, 카카오톡이 사실상 유일한 공유 경로라는 주장, 페이지 수만으로 검색 유입 부재를 설명하는 주장은 근거가 없어 사용하지 않는다.

## 3. 실험 지표 제안

| 지표 | 기준값 | 승인 후 2주 목표 가설 |
| --- | --- | --- |
| UTM이 있는 `page_view` 이벤트 | 원기록 0, 재검증 필요 | 100행. 방문자 100명과 구분 |
| 사전 신청 행 | 원기록 1, 재검증 필요 | 누적 10행. 중복·테스트 제외 기준 필요 |
| 방문→신청 전환 | 동일 기간·연결 기준 미확보 | 채널별 동일 코호트 분모·분자 정의부터 완료 |
| 게시물 도달·팔로워 변화 | 채널 인사이트 미확보 | 게시 전 기준값 대비 변화 관찰 |

목표는 예측이나 성과 보장이 아니다. 100 이벤트를 모아도 A/B 유의성이 자동으로 확보되지는 않는다. 목표 효과 크기와 필요한 표본을 별도로 판단한다. 실제 신청 수를 부풀리거나 팔로워·좋아요를 구매하지 않는다.

## 4. 승인 후 편성 후보

D1은 승인 후 실제 시작일이다. 릴스 일 1개를 확정하지 않고 아래 소재의 제작 여력을 먼저 확인한다.

| 기간 | 소재 후보 | 채널 후보 |
| --- | --- | --- |
| D1~3 | 릴스 #01·#02, 등기부 #01 | 인스타·스레드·X |
| D4~7 | 캐러셀 등기부 #01, 제작 기록, 릴스 #03, 만화 #01 | 소재에 맞춰 선택 |
| D8~11 | 릴스 #04·#05, 임대인 노트 #01, 캐러셀 등기부 #03 | 소재에 맞춰 선택 |
| D12~14 | 릴스 #06, 등기부 #05, 만화 #02 | 소재에 맞춰 선택 |
| 이후 | 릴스 #07·#08 | 앞선 반응과 검토 결과에 따라 결정 |

전 소재가 게시 전 검토 대상이다. D14에 채널별 결과를 검토하되 오류·오해·민원이 발생하면 즉시 중단·수정한다. 2주간 편성을 무조건 유지하지 않는다.

## 5. 다음 담당과 완료 조건

CMO가 조회 근거와 게시 이력을 정리하고 보드에 소재·채널·실험 범위 결정을 요청한다. CTO는 기술 제안을 채택할 경우 현행 동작과 공수를 검토한다. 이 문서의 커밋은 내부 제안서 보관 완료이며 코드 구현·배포·외부 게시 승인을 의미하지 않는다.
