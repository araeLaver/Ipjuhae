# 검색 조건 저장과 신규 매물 알림

## 동작
- 매물 찾기에서 `저장한 검색`을 열어 현재 키워드·지역·유형·정렬을 저장한다.
- 로그인 계정에 최대 10개 저장하며 동일 조건은 중복 저장하지 않는다.
- 저장 조건 적용, 신규 매물 알림 켜기/끄기, 삭제를 제공한다.
- 알림은 기존 앱 알림 센터에 표시한다. 이메일·SMS·외부 푸시는 발송하지 않는다.
- 알림을 켠 뒤 등록된 공개 매물만 대상이다. 탈퇴 임대인과 본인 매물은 제외한다.
- 다시 켜면 재활성화 시점부터 새 매물을 찾는다. 꺼진 기간의 매물을 몰아서 알리지 않는다.
- 1회에 검색 20개, 검색별 매물 20건을 처리하고 나머지는 후속 주기에 처리한다. 계정 전체 설정 수에 따라 알림이 늦어질 수 있다.
- 검색 조건별로 매물 1개당 1번만 알린다. 겹치는 조건을 따로 저장하면 각각 알림을 받을 수 있다.
- 알림 클릭 URL에 저장 조건을 보존한다.
- 계정 삭제 시 저장 조건·중복 방지 기록을 삭제하고 데이터 내보내기에 저장 조건을 포함한다.

## 운영 활성화 순서
1. 기존 배포 절차에 따라 `migration-046-saved-searches.sql`을 포함한 DB 마이그레이션을 적용한다.
2. 신규 코드를 빌드·배포한다. Docker 이미지에는 `build/saved-search-alerts.cjs`도 포함된다.
3. 서버 환경에 `SAVED_SEARCH_ALERTS_ENABLED=true`를 설정한 뒤 서버를 재시작한다.
4. 실제 계정으로 조건을 저장하고 알림을 켠 뒤 해당 조건의 신규 매물을 등록하여 알림을 확인한다.
5. 같은 매물 재처리 시 알림이 늘지 않는지, 해제 후 신규 매물에는 알림이 없는지 확인한다.

서버 내부에서 60초마다 검사한다. 동일 프로세스 중첩 실행은 막고, 여러 인스턴스는 행 잠금과 SKIP LOCKED로 검색을 분담한다. 신규 매물 중복 기록과 알림은 같은 트랜잭션에서 커밋해 실패 시 같이 롤백한다.

외부 스케줄러를 쓰는 환경에서는 `GET /api/cron/saved-searches`를 `Authorization: Bearer <CRON_SECRET>`으로 호출한다. 비밀키 미설정·불일치는 401, 알림 기능 비활성화 상태는 처리하지 않고 반환한다. 앱 내부 스케줄러와 함께 호출해도 중복 방지된다.

비활성화하려면 `SAVED_SEARCH_ALERTS_ENABLED=false`로 서버를 재시작한다. 기존 조건은 남고 UI에서 신규 알림 신청이 차단된다. 기존 알림 해제와 조건 저장·삭제는 가능하다. 전체 기능을 다시 켤 때 이미 알림을 켜 둔 검색은 중단 기간의 신규 매물을 처리하므로, 장기간 중단 후 재개 시 운영 검토가 필요하다.

## 검증
- 전체 Vitest: 941개 통과, 24개 건너뜀. 이 중 신규 실제 DB 6개는 아래 별도 실행으로 통과했다.
- 실제 PostgreSQL: 6개 통과. 로컬 호스트만 허용하며 고유 임시 스키마를 만든 뒤 삭제한다.
- 신규 UI 테스트 4개: 저장 실패 복구, 로그인 복귀 조건, 조건 적용·알림 변경·삭제, 기능 비활성화 표시.
- 신규 API 테스트 5개: 인증·입력 검증, 기능 비활성화, cron 인증·실패 응답.

```sh
SAVED_SEARCH_TEST_DATABASE_URL=postgresql://<local-user>@127.0.0.1:5432/ipjuhae_db \
  npx vitest run __tests__/db/saved-searches-real-db.test.ts
```

현재 작업은 구현과 로컬 검증이다. 운영 마이그레이션·배포·활성화는 실행하지 않았다.
- 프로덕션 빌드 및 별도 타입 검사 통과. ESLint 오류 없음(기존 img 최적화 경고 1개).
- 실제 Chromium 브라우저 검증 통과: URL에서 조건 복원 → 저장 → 알림 끄기 → 저장 조건 적용 → 삭제, 페이지 오류 0개. API는 fixture 응답이며 실제 DB 테스트와 별개다.
- 브라우저 재실행: 로컬 프로덕션 서버를 실행한 뒤 `node scripts/qa/check-saved-searches-browser.mjs`.
